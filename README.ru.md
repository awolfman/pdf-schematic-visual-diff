# pdf-schematic-visual-diff

Автоматизированный Git-хук (`pre-commit`) для визуального контроля качества изменений в PDF-схемах и чертежах, разработанный специально для репозиториев аппаратной разработки (CAD/EDA) с поддержкой **Git LFS**.

С недавними обновлениями проект теперь поддерживает **парсинг нетлистов Cadence Allegro / OrCAD Capture** и структурную валидацию параллельно с попиксельным визуальным сравнением.

> ⚡ **Когда срабатывает хук:** Скрипт выполняется автоматически **в момент запуска `git commit`**. Он перехватывает индексированные файлы PDF, на лету извлекает данные из хранилища Git LFS и разделяет свое поведение в зависимости от режима бэкенда, определенного в файле `.schematic-backend`. Он создает визуальный отчет с именем `[name]_diff.pdf`, а в режиме Cadence также проверяет и обновляет файлы отслеживания семантического нетлиста перед автоматическим добавлением их в текущий коммит.

## 📂 Структура проекта

Проект превратился в структурированный набор специализированных инструментов и файлов конфигурации состояний:

```text
project/
├── .git/
│   └── hooks/
│       └── pre-commit              # Главная точка входа Git-хука
├── tools/
│   ├── pdf-diff.sh                 # Движок низкоуровневого визуального сравнения PDF
│   ├── check_cadence_netlist.sh    # Основной диспетчер конвейера валидации Cadence
│   ├── check_capture_export.py     # Скрипт проверки корректности экспорта
│   ├── parse_capture_netlist.py    # Извлечение семантических данных из файлов OrCAD
│   └── compare_netlists.py         # Оценка структурных изменений между коммитами
├── netlists/
│   └── cadence.json                # Версионируемая базовая база данных нетлиста
├── .schematic-backend              # Конфигурационный файл режима работы (pdf / cadence)
└── .gitignore                      # Правила исключения рабочих папок
```

> ⚠️ **Важно:** Не добавляйте каталог `tools/` и файл `netlists/cadence.json` в `.gitignore`. Они должны версионироваться для обеспечения согласованной автоматизации во всех рабочих окружениях.

## ⚙️ Режимы работы бэкенда

Инструмент адаптирует свое поведение с помощью конфигурационного файла `.schematic-backend`. Этот файл должен быть явно добавлен в индекс:
```bash
git add .schematic-backend
```

Допустимые значения внутри `.schematic-backend`:
* `pdf` — Стандартный режим. Выполняет только визуальное сравнение PDF-diff.
* `cadence` — Расширенный режим валидации для проектов Cadence Allegro / OrCAD Capture.

### 🔄 Конвейер выполнения Cadence
Если установлен режим `cadence`, хук pre-commit выполняет следующую последовательность шагов:
1. **PDF-diff**: Запускает визуальное попиксельное сравнение чертежей.
2. **Проверка целостности экспорта**: Запускает `check_capture_export.py` для сканирования `netlist.log` и файлов `.dat` на наличие ошибок компиляции.
3. **Разбор нетлиста**: Запускает `parse_capture_netlist.py` для обработки структурного содержимого файлов `pstchip.dat`, `pstxprt.dat` и `pstxnet.dat`.
4. **Получение базовой модели**: Извлекает исходную модель схемы из предыдущего коммита истории (`HEAD`).
5. **Семантическое сравнение**: Вызывает `compare_netlists.py` для сравнения модели текущего рабочего пространства с базовой.
6. **Умная блокировка**: Коммит отклоняется **только** в случае обнаружения явных ошибок или неопределенностей (неоднозначностей) в структуре.
7. **Обновление базы отслеживания**: Регенерирует и обновляет базовый файл отслеживания по пути `netlists/cadence.json`.
8. **Автоматическое индексирование**: Выполняет команду `git add netlists/cadence.json` для включения изменений базы данных в текущий коммит.

## ✨ Логика цветового кодирования чертежей

Алгоритм работает на низком уровне, сравнивая яркость пикселей путем вычитания векторных каналов (`-compose MinusSrc`), что позволяет ему точно фиксировать структурные изменения в CAD-схемах:

- **Удаление компонента**: Все удаленные символы/компоненты подсвечиваются **синим** цветом.
- **Добавление компонента или изменение RefDes**: Подсвечиваются **красным** цветом.
- **Перемещение компонента**: Старая позиция компонента на схеме становится **синей**, а новая — **красной**.

## 🚀 Особенности реализации

- **Двойная валидация (семантическая и визуальная)**: Сочетает абсолютное улавливание графических изменений с проверкой топологии электрического нетлиста.
- **Полная интеграция с Git LFS**: Автоматически обнаруживает текстовые указатели LFS в истории коммитов и безопасно выполняет процедуру `smudge` в изолированном рабочем пространстве.
- **Устойчивость к сглаживанию (Anti-Aliasing)**: Матричные операции с аппаратным ускорением в сочетании с морфологическим расширением (`Dilate Disk:1`) улавливают микросдвиги векторных линий толщиной в 1 пиксель, предотвращая ложные срабатывания.
- **Высокая производительность**: Рендеринг страниц и обработка пикселей полностью параллелизованы с использованием `GNU Parallel` в сочетании с многопоточной пакетной обработкой `pdftocairo`. Внутренние границы выполнения установлены так, чтобы избежать перегрузки ядер процессора.

## 🔧 Настройка лимитов ресурсов ImageMagick

При обработке больших CAD-документов (таких как чертежи размеров A1 или A0 при 300 DPI) стандартных параметров безопасности ImageMagick может не хватить, что приведет к ошибкам вида `Image width exceeds user limit` или критическому замедлению из-за кэширования на счет жесткого диска.

### Рекомендуемые профили политик

Измените конфигурационный файл безопасности ImageMagick (обычно он находится по адресу `/etc/ImageMagick-7/policy.xml` or `/etc/ImageMagick-6/policy.xml`).

Добавьте или обновите следующие параметры внутри тегов `<policymap>` прямо перед закрывающим элементом `</policymap>`:

```xml
<policymap>
  <!-- Максимальные растровые границы одного изображения (16384 x 16384 пикселей) -->
  <policy domain="resource" name="width" value="16KP"/>
  <policy domain="resource" name="height" value="16KP"/>
  
  <!-- Максимальная общая площадь кадра в мегапикселях (128 МП) -->
  <policy domain="resource" name="area" value="128MP"/>
  
  <!-- Ограничения на использование оперативной памяти и маппинга памяти -->
  <policy domain="resource" name="memory" value="2GiB"/>
  <policy domain="resource" name="map" value="4GiB"/>
  
  <!-- Лимит временного дискового пространства, если выделенная память заполнится -->
  <policy domain="resource" name="disk" value="8GiB"/>
  
  <!-- Потолок времени выполнения для одного процесса команды (10 минут) -->
  <policy domain="resource" name="time" value="600"/>
</policymap>
```

> 📌 **Примечание:** Хотя скрипт pre-commit пытается динамически переопределять и изолировать эти среды ресурсов для своих фоновых процессов на лету, ручное редактирование global системы `policy.xml` гарантирует предсказуемое поведение во время индивидуальных сессий ручной отладки.

## ⚠️ Важно: `magick` (IM 7) против `convert` (IM 6)

Скрипт опирается на команду **`magick`**, которая является нативным интерфейсом для **ImageMagick 7**. В большинстве дистрибутивов менеджер пакетов устанавливает **ImageMagick 6**, где та же функциональность доступна через команду **`convert`**.

### Если у вас ImageMagick 6

Замените `magick` на `convert` внутри скрипта с помощью этой команды:
```bash
sed -i 's/magick/convert/g' .git/hooks/pre-commit
```

## 💻 Настройка репозитория и установка хука

### Шаг 1. Инициализация Git LFS для PDF и исходников CAD

Выполните следующие команды в корне вашего репозитория в зависимости от вашей CAD-системы:

* **Для Cadence Allegro / OrCAD Capture:**
  ```bash
  git lfs install
  git lfs track "*.pdf" "*.dsn"
  git add .gitattributes
  ```

* **Для Altium Designer:**
  ```bash
  git lfs install
  git lfs track "*.pdf" "*.SchDoc"
  git add .gitattributes
  ```

* **For KiCad:**
  ```bash
  git lfs install
  git lfs track "*.pdf" "*.kicad_sch"
  git add .gitattributes
  ```

### Шаг 2. Настройка окружения и исключений для Cadence

При инициализации пайплайна отслеживания **Cadence** текстовые логи сборки и промежуточные бинарные файлы нетлиста должны быть изолированы от индекса Git.

1. Выполняйте экспорт нетлиста из OrCAD Capture строго в служебную директорию проекта. Выходные файлы на стороне экспортера должны иметь фиксированные имена:
   * `.capture-export/netlist.log`
   * `.capture-export/pstchip.dat`
   * `.capture-export/pstxprt.dat`
   * `.capture-export/pstxnet.dat`

2. Добавьте этот каталог экспорта в файл конфигурации `.gitignore`, чтобы бинарные матрицы `.dat` никогда не индексировались:
   ```text
   .capture-export/
   ```

3. Возьмите на постоянное версионирование все базовые модели инфраструктуры, конфигурационные ключи и скрипты автоматизации:
   ```bash
   git add .schematic-backend .gitignore tools netlists/cadence.json
   ```

> 🚨 **Критическое ограничение:** Валидационный скрипт (`check_capture_export.py`) не может программно гарантировать, что сгенерированные файлы `.dat` соответствуют абсолютно последнему сохраненному состоянию основного файла проекта `.dsn`. Поэтому перед запуском команды `git commit` в режиме Cadence вы **должны сначала вручную выполнить экспорт нетлиста Capture в каталог `.capture-export`**.

## 🔧 Устранение неполадок

### Все страницы помечены как «Modified», хотя схема не менялась

Это вызвано **различиями в поведении рендеринга poppler** между версиями PDF или несоответствиями внедрения шрифтов. Проверьте файлы с помощью `pdfinfo`:
```bash
pdfinfo old.pdf | grep -E "Pages|Page size"
```

Если размеры страниц совпадают, но ложные срабатывания на всю страницу сохраняются, попробуйте снизить чувствительность, увеличив значение `THRESHOLD` через переменные окружения перед запуском коммита:
```bash
export PDF_DIFF_THRESHOLD="2%"
git commit -m "Commit message"
```

> 💡 **Важно при использовании CUPS-PDF (Linux):**
> Этот принтер преобразует весь текст напрямую в векторные кривые (графические контуры). Для инструмента визуального сравнения это идеальный сценарий, так как формы букв «замораживаются» как геометрия, убирая любую зависимость от пакетов шрифтов локальной системы.
>
> ⚠️ **Критические ограничения:**
> * Обе сравниваемые версии должны быть сгенерированы через CUPS-PDF с использованием идентичных настроек формата и масштабирования.
> * Настоятельно рекомендуется поддерживать один и тот же пайплайн экспорта, включая хост-приложение и Wine. Обновление системного драйвера или Ghostscript также может изменить результат рендеринга.
> * Сравнение результатов, полученных из разных виртуальных принтеров, не поддерживается. Это может подсветить значительную часть страницы, даже если исходная схема не изменилась.
> * Хут сравнивает чисто визуальный вид страниц, а не электрические соединения или семантику компонентов. Любое визуальное несоответствие потенциально помечается как изменение.

### Коммит обрабатывается слишком долго

По умолчанию скрипт выполняет рендеринг при `DPI=300`. Для больших многолистовых чертежей формата A1 это может быть ресурсоемко. Снизьте разрешение сравнения до 150 или 200 DPI:
```bash
export PDF_DIFF_DPI=150
export PDF_DIFF_OUTPUT_DPI=150
git commit -m "Commit with faster diff calculation"
```

Этого разрешения остается полностью достаточно для отслеживания компонентов и позиционных обозначений (RefDes).

## 🐳 Интеграция с CI/Docker

Если вы запускаете этот хук внутри среды CI/CD, вы можете использовать готовую конфигурацию Docker-образа:

```dockerfile
FROM python:3.12-slim

RUN apt-get update && apt-get install -y     git git-lfs imagemagick poppler-utils parallel     && rm -rf /var/lib/apt/lists/*

RUN pip install img2pdf

# Замена magick на convert для окружений с ImageMagick 6
RUN sed -i 's/magick/convert/g' /usr/local/bin/pre-commit-hook
```

Пример конфигурации рабочего процесса GitLab CI:

```yaml
stages:
  - validate

visual-diff:
  stage: validate
  image: your-registry/pdf-diff-runner:latest
  script:
    - git lfs install
    - git lfs pull
    - .git/hooks/pre-commit
  only:
    - merge_requests
```
